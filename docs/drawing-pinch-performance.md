# 드로잉 핀치 최적화: 좌표 계산은 손을 뗄 때 한 번만

보드의 그림은 이미지 파일이 아니라 **점 좌표를 연결한 SVG 선**이다. 두 손가락으로 확대·회전하는 핀치에서는 선의 모양을 편집하지 않는다. 같은 그림을 다른 위치·각도·크기로 보여주면 된다.

개선 전 구현은 이 과정에서 모든 점을 반복 계산했다. 개선 방향은 **조작 중에는 원본 경로에 transform만 적용하고, 조작이 끝나면 좌표를 한 번 확정하는 것**이다.

## 개선 전 구현의 반복 비용

손가락 이동 이벤트마다 다음 작업이 발생한다.

```text
확대율·회전각 계산 → 모든 점의 좌표 변환 → 새 배열·점 객체 생성
→ React 상태 변경 → 전체 SVG 경로 문자열 재생성 → 브라우저가 변경된 경로 처리
```

예를 들어 점 2,000개인 선에서 초당 60번 변환하면, 좌표 변환만 초당 12만 점이다. 여기에 문자열 생성과 화면 갱신이 붙고, 버려지는 배열·객체·문자열은 GC의 회수 대상이 된다. 이 숫자는 설명용 예시이며 실제 측정값은 아니다.

완성된 다른 선은 `memo`로 경로 재생성을 피할 수 있다. 문제는 핀치 중인 선의 점 배열이 계속 바뀌어 이 최적화를 활용하지 못한다는 것이다.

## 개선: 경로를 유지하고 표시만 변환

핀치 시작 시 원본 점 목록을 고정한다. 조작 중에는 확대율·회전각·이동량으로 transform을 계산하고, 화면 반영을 `requestAnimationFrame`으로 프레임당 한 번 모은다. 모든 점을 순회할 필요는 없다.

마지막 손가락을 떼면 최종 변환을 원본 점에 한 번 적용한다. 현재 단순 드래그도 SVG의 `<g transform>`으로 미리보기를 표시하고, 종료 시 좌표를 확정하는 방식을 사용한다.

| 비용                 | 현재 핀치                  | 개선 후                              |
| -------------------- | -------------------------- | ------------------------------------ |
| 전체 점의 좌표 변환  | 이동 이벤트마다            | 조작 종료 시 한 번                   |
| 점 배열·객체 생성    | 이동 이벤트마다            | 최종 좌표 확정 시                    |
| SVG 경로 문자열 생성 | 미리보기 렌더마다          | 최종 좌표 확정 시                    |
| 브라우저 페인트      | 경로 변경에 따른 처리 필요 | 합성 조건이 맞으면 조작 중 생략 가능 |

점이 N개이고 이동 이벤트가 E번이라면, 좌표 처리의 작업량을 **O(N×E)에서 O(N+E)**로 줄이는 방향이다. 이는 좌표 처리에 대한 설명이며 화면 전체의 렌더링 비용까지 같은 비율로 줄어든다는 뜻은 아니다.

## Chrome·Safari에서 페인트도 줄일 수 있는 이유

브라우저는 요소를 레이어에 그린 뒤 화면에 합성할 수 있다. 그림 내용이 유지되고 레이어의 transform만 바뀌면, **기존에 그린 결과를 재사용해 repaint를 생략할 수 있다.**

Chrome은 Chromium 89부터 SVG 애니메이션의 하드웨어 가속을 지원하며, 공식 예제에서 반복 repaint가 사라지는 사례를 보여준다. Safari의 엔진인 WebKit도 자체 레이어를 가진 요소는 repaint 없이 재합성만으로 움직일 수 있다고 설명한다. [Chrome 공식 자료](https://developer.chrome.com/blog/hardware-accelerated-animations), [WebKit 공식 Layers 문서](https://webkit.org/web-inspector/layers-tab/).

다만 **transform 지원과 우리 핀치의 페인트 생략은 별개**다. CSS 애니메이션 사례가 스크립트로 갱신하는 `<g transform>`의 처리까지 보장하지는 않는다. `will-change`도 최적화 힌트이며, 레이어를 늘리면 메모리 비용이 생긴다. 그림 하나의 바깥 `<svg>`에 CSS transform을 적용하는 미리보기를 실험 후보로 삼되, 실제 합성 여부를 확인해야 한다.

확대 시에는 선명도를 위해 픽셀을 다시 만드는 **재래스터화** 비용이 발생하거나, 기존 결과를 확대해 일시적으로 흐려질 수도 있다. Chrome은 이 성능·화질의 절충을 설명하고, WebKit에도 확대 시 픽셀화에 관한 이슈가 있다. 해당 이슈가 우리 앱에서 재현된다는 뜻은 아니다. [Chrome 재래스터화 설명](https://developer.chrome.com/blog/re-rastering-composite), [WebKit 이슈 #27684](https://bugs.webkit.org/show_bug.cgi?id=27684).

## 적용 시 지켜야 할 동작과 검증

- 미리보기와 최종 좌표 계산에 같은 변환을 사용한다. 확대에 따른 선 굵기와 선택 박스도 일치시킨다.
- 핀치에서 한 손가락 이동으로 이어져도 변환을 유지한다. 마지막 입력까지 반영하고, 최종 경로 교체와 임시 transform 해제를 함께 처리해 화면이 튀지 않게 한다.
- 같은 긴 선으로 변경 전후의 JS 시간·Paint·Raster 작업을 비교한다. Safari에서는 Layers의 Paint count와 메모리 사용량, 확대 중·종료 후 선명도도 확인한다. [Apple Web Inspector 설명](https://developer.apple.com/videos/play/wwdc2020/10646/).

현재는 이 방향으로 구현했다. 이동 중에는 ref에 변환만 보관하고 rAF에서 선택 SVG와 선택 박스의 CSS transform을 갱신한다. 드래그·재핀치를 이어가도 마지막 손가락을 뗄 때 좌표와 선 굵기를 한 번 확정한다. 선택 박스의 테두리 두께는 확대에 맞춰 보정한다.

개발 서버·CPU 6×에서 같은 600회 이동을 비교했다. 재생 시간은 **11.18초 → 2.58초**, 메인 스레드 작업 누적은 **11,158ms → 977ms**, SVG Paint는 **289회 → 2회**였다. 화면 전체 Paint는 약 99ms → 59ms로 줄었지만 선택 박스 등의 페인트는 남는다. 개발 모드 비용을 포함한 단일 비교이며, 배포 환경·Safari 실기기의 개선 폭을 보장하지 않는다.

## 데스크톱에서 변경 전후 성능 기록

마우스만 있어도 [핀치 재생 스크립트](../scripts/devtools/drawing-pinch.js)로 기존 입력 핸들러에 두 포인터의 확대·회전을 전달할 수 있다.

1. 변경된 앱을 새로고침하고, **이동 모드에서 긴 그림 하나를 선택**한다. 그림 중심이 화면 안에 있어야 한다.
2. 저장소 루트의 터미널에서 `pbcopy < scripts/devtools/drawing-pinch.js`로 복사한 뒤 DevTools Console에 붙여넣어 실행한다.
3. Console에서 `ppottoPinch()`를 실행하고 **5초 안에 Performance 녹화**를 시작한다. 재생 중에는 보드를 조작하지 않는다.
4. 완료 메시지가 뜨면 녹화를 중지한다. Timings의 `ppotto-pinch` 구간에서 Main의 JS 실행·Paint와 Raster 작업을 확인한다. `ppotto-pinch:release`는 손을 떼는 시점이다.
5. 기록을 내보내 보관하고, **이동 모드의 X로 취소**한다. 변경 후에도 같은 그림·브라우저·화면 크기·측정 설정으로 반복한다.

기본값은 300단계, 총 600회의 이동 이벤트다. 정상 종료 시 시작 좌표로 돌아오며, `Esc`로 중단하면 중간 위치가 남을 수 있으므로 X로 취소한다. 재생 시간은 화면 주사율과 부하에 따라 달라진다. 합성 이벤트이므로 앱의 JS·렌더링 비교용이며, 실제 터치 입력 지연이나 실기기 성능을 대신 측정하지는 않는다.
