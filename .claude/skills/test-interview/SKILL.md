# TDD 인터뷰

테스트 작성 전에 사용자를 인터뷰하여 기능의 동작과 이번 구현 범위를 확정한다.

목표는 모든 엣지 케이스의 구현이 아니다. 사용자가 미처 생각하지 못한 상황까지 발견한 뒤, 각 케이스를 **① 이번 구현에 포함 ② 이번 구현에서 제외 ③ 미결 `[팀확인]`** 중 하나로 분류하고, 포함 케이스만 `it.todo` 골격으로 만든다.

**이 스킬의 산출물은 `it.todo` 골격 파일까지다.** 테스트 본문 작성과 구현은 이후 작업이며, 본문을 채울 때는 test-writing 스킬을 따른다.

흐름: 컨텍스트 파악 → 인터뷰 → 분류 정리 → 사용자 승인 → `it.todo` 골격 생성. 골격 생성 전에는 테스트 본문도 구현도 시작하지 않는다.

## 1. 컨텍스트 파악

기능 설명, PRD, 유사 기능 코드, API 스키마·타입, 기존 테스트 컨벤션을 먼저 확인한다. 문서나 코드에 이미 명확히 정의된 동작은 다시 묻지 않는다. 자료가 부족할 때만 사용자에게 요청한다.

인터뷰 시작 전에 현재 이해한 기능과 불명확한 부분을 짧게 요약한다.

## 2. 인터뷰

### 진행 규칙

- 한 번에 질문 하나. 답을 듣고 다음 질문을 정한다.
- 추상적 정책명이 아니라 구체적 상황을 묻는다.
  - 나쁨: "에러 처리는 어떻게 하나요?"
  - 좋음: "저장 요청이 실패하면 사용자가 입력한 내용은 그대로 유지되나요?"
- 정책을 임의로 만들지 않는다. 일반적 관행을 정답처럼 강요하지 않는다. 사용자가 아직 결정하지 않았다면 `[팀확인]`으로 기록하고 넘어간다.
- 엣지 케이스를 발견해도 자동으로 구현 범위에 넣지 않는다. 범위가 불명확하면 묻는다: "이 경우도 이번 구현에 포함할까요, 이번에는 지원하지 않을까요?"
- 이미 답한 내용을 다시 묻지 않는다. 사용자가 종료를 요청하면 즉시 정리 단계로 간다.

### 질문 카테고리

누락 방지용 체크리스트. 순서대로 검토하되 현재 기능과 관련 있는 것만 질문하고, 형식적 질문은 만들지 않는다.

1. **렌더 조건** — 최초 진입, 데이터 없음, 로딩, 완료, 필수 데이터 누락, 상태별 노출.
   예: "목록이 비어 있으면 안내 화면이 보이나요, 아무것도 안 보이나요?"
2. **인터랙션** — 클릭·입력·선택, 취소, 뒤로 가기, 키보드, 비활성 조건, 외부 콜백.
   예: "선택을 취소하면 기존 선택값을 유지하나요, 초기화하나요?"
3. **비동기와 에러** — 요청 중 UI, 성공·실패 피드백, 네트워크 오류, 재시도, 실패 후 입력값 유지, 부분 성공.
   예: "일부 파일만 업로드에 실패하면 전체를 실패 처리하나요, 성공한 파일은 유지하나요?"
4. **경계값** — 0개와 1개, 최대값과 초과, 빈 문자열, 글자 수 제한, 중복 데이터, 잘못된 형식, 긴 텍스트 잘림.
   예: "최대 100장을 선택한 상태에서 한 장을 더 고르면 추가 선택을 막나요?"
5. **중복과 타이밍** — 더블클릭·연타, 요청 중 재실행, 빠른 연속 입력, 응답 순서 역전, 응답 전 페이지 이탈.
   예: "검색어를 빠르게 바꿨을 때 이전 요청이 늦게 도착하면 그 응답을 무시하나요?"
6. **권한과 상태 조합** — 로그인 여부, 권한·소유자 차이, 이미 처리된 대상, 삭제·만료된 대상.
   예: "이미 삭제된 항목을 다시 삭제하면 오류를 보여주나요, 성공으로 처리하나요?"
7. **상태 유지** (필요한 기능만) — 새로고침, 페이지 이동 후 복귀, URL 반영, 로컬·서버 저장.
   예: "작성 중 다른 페이지로 이동했다 돌아오면 입력 내용이 유지되나요?"

### 기능 유형별 추가 확인

- **순수 함수**: 입력·출력, 경계값, 잘못된 입력, 정렬·우선순위, 불변 조건.
- **파일 생성기·스크립트**: 입출력 경로, 덮어쓰기, 삭제된 입력의 결과 제거, 일부 실패 시 기존 결과 보존, 재실행.
- **API 클라이언트**: 요청 형식, 응답·오류 변환, 인증 만료, 취소·재시도, 중복 요청.
- **UI 컴포넌트**: 상태별 렌더링, 사용자 조작, 공개 props·콜백, 비활성, 접근성, 빈 데이터·긴 텍스트.

### 종료 조건

정상 흐름·주요 실패·중요한 경계값과 타이밍이 확인됐고, 발견한 케이스를 분류할 수 있으며, 추가 질문이 구현 범위를 실질적으로 바꾸지 않으면 종료를 제안한다. 새로운 미결이 반드시 나와야 하는 것은 아니다.

종료 전 마지막으로 묻는다: "이번 구현에서 의도적으로 지원하지 않을 상황이 더 있나요?"

## 3. 분류 정리와 승인

인터뷰가 끝나면 아래 형식으로 정리하고 사용자 승인을 받는다. 승인 전에는 골격을 만들지 않는다.

```md
## <기능명> 동작 범위

### 이번 구현에 포함

- [렌더] 최초 진입 시 기존 데이터를 표시한다.
- [에러] 저장 실패 시 입력값을 유지한다.
- [중복] 저장 응답 전 다시 눌러도 요청은 한 번만 발생한다.

### 이번 구현에서 제외

- [오프라인] 네트워크 복구 후 자동 재시도 — 사유: MVP 범위 밖

### 미결 [팀확인]

- [이탈] 저장 중 페이지 이탈 시 완료 알림 표시 위치 — 확인 대상: 기획
```

- 구현 방법이 아니라 외부에서 관찰 가능한 동작으로 작성한다.
- 발견한 케이스를 임의로 생략하지 않고, 제외 케이스는 사유를 기록한다.

## 4. it.todo 골격 생성

승인된 **포함** 케이스만 골격으로 만든다.

### 파일 분할

골격 파일을 쓰기 전에 이번 기능이 여러 구현 단위(컴포넌트·모듈)로 나뉘는지 확인한다.

- 기존 코드를 수정·확장하는 경우: 이미 있는 파일 구조를 그대로 따른다.
- 신규 기능이라 구현 단위가 아직 안 정해진 경우: 사용자에게 짧게 확인한다. 예: "이 기능, 컴포넌트 몇 개로 나눌 계획이에요?"
- 자기 상태·로직·인터랙션을 가진 단위마다 별도 골격 파일을 만든다. 조건·로직 없이 표시만 하는 하위 컴포넌트는 별도 파일을 만들지 않는다 — 상위 단위의 테스트에서 간접적으로 커버된다.
- `describe`는 하나의 골격 파일 안에서 시나리오(렌더/에러/중복 등)를 그룹핑하는 용도로만 쓴다. 구현 단위 경계를 넘어 여러 단위를 한 파일에 몰아넣지 않는다.
- 이 분할은 파일 조직 문제이며, 테스트가 검증하는 내용(공개 동작 vs 내부 구현)과는 무관하다. 골격 생성 이후 test-writing 스킬로 본문을 채울 때도 이 분할은 유지되며, test-writing은 이미 정해진 파일 구조 안에서 본문만 작성한다.

### 골격 작성

- 프로젝트의 테스트 러너·파일 위치 컨벤션을 따른다.
- 모든 케이스는 `it.todo`로 시작하고, 본문은 작성하지 않는다.
- 테스트 이름은 구체적인 한국어 동작 문장으로 쓴다.
- 제외·미결 케이스는 `it.todo`로 넣지 않는다. 대신 파일 상단 주석 블록에 기록하여, 해당 테스트 파일이 **이번 구현에서 합의한 동작 범위의 SoT** 역할을 하게 한다.

```ts
/**
 * 동작 범위 (2026-07-23 인터뷰)
 * 제외: 오프라인 자동 재시도 — MVP 범위 밖
 * [팀확인] 저장 중 페이지 이탈 시 완료 알림 위치 — 기획 확인 대기
 */
describe('프로필 저장', () => {
  it.todo('저장 버튼을 누르면 현재 입력값으로 저장 요청을 보낸다');
  it.todo('저장 중에는 저장 버튼이 비활성화된다');
  it.todo('저장 실패 시 입력값을 유지한다');
  it.todo('저장 응답 전 다시 눌러도 요청은 한 번만 발생한다');
});
```

골격 생성 후 보고한다: 생성한 파일, todo 수, 주석에 기록한 제외·미결 케이스. 그리고 골격 커밋을 제안한다 (골격 커밋 = 동작 명세 확정 시점).

## 5. 이후 작업

- 테스트 본문 작성과 구현은 사용자가 요청할 때 진행하며, 본문 작성 시 test-writing 스킬의 원칙(공개 동작 검증, 구현 비결합 등)을 따른다.
- 구현 중 새로운 케이스가 발견되면 바로 구현하지 않는다. 사용자에게 알리고 포함(→ `it.todo` 추가)·제외(→ 주석 추가)·`[팀확인]`(→ 주석 추가) 중 하나로 재분류한 뒤 진행한다.

## 금지 사항

- 인터뷰와 승인 전에 테스트나 구현을 시작하지 않는다.
- 여러 질문을 한꺼번에 나열하지 않는다.
- 정책을 임의로 결정하지 않고, 엣지 케이스를 자동으로 구현 범위에 넣지 않는다.
- 제외·미결 케이스를 `it.todo`로 만들지 않는다 (상단 주석에만 기록).
- 테스트 작성 편의를 위해 요구사항을 바꾸지 않는다.
